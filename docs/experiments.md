# Windows 原生播放器實驗

日期：2026-10-27。環境：Windows build 22621、.NET runtime 8.0.6、12 個邏輯處理器、Release build。

## 方法

- 使用與正式視窗相同的 `WindowsAudioPlayer`，在隱藏視窗／正常 WinForms 訊息迴圈內執行。
- 程式靜音，不改變系統音量。透過官方流程取得來源，不經 TWeFM，不將音訊落盤。
- 閒置取樣 5 秒；每台等到 Playing，暖機 3 秒，穩態取樣 15 秒，Stop 後再取樣 3 秒。
- 每秒取樣程序 private bytes 與 working set；CPU 為區間內程序 CPU 時間除以牆鐘時間，再除以 12，與工作管理員的全機百分比概念一致。
- 播放狀態不是唯一通過條件，還須沒有播放失敗，且播放時鐘持續前進。後續版本要求至少前進取樣時間的 90%。
- 原始 JSON 留在被 Git 忽略的 `artifacts/`，只記主機名，沒有帶簽章的串流網址。

## 加嚴重測

新增來源是否帶影像的診斷，並以「取樣期間播放時鐘前進至少 90%」重跑六台。五台通過；**飛碟未通過**：15 秒期間僅前進 10.25 秒，事件紀錄有多次 Buffering。此輪程式以 exit code 2 回報未全數通過，而不是只看到 Playing 就宣稱穩定。

六台都曾在首輪完成短測，但目前不能說六台已可靠、無卡頓。飛碟需另做較長的網路／播放引擎比較，中廣也仍可觀察到開播緩衝。KISS 重測 working set 約 176.28 MiB、private 約 138.99 MiB，影像額外開銷仍可重現。

## KISS 追查

獨立程序重測 60 秒，時鐘前進 60.24 秒：private 平均 **136.80 MiB**、working set 平均 **175.67 MiB**、CPU 全機平均 **0.076%**。不是只在切台當下出現的單次高峰。

進一步記錄 Windows 引擎資訊，KISS 回報 **HLS 並非 audio-only，影像尺寸為 640×360**。不顯示影像不等於不處理影像。

嘗試透過 `MediaPlaybackItem.VideoTracks.SelectedIndex = -1` 取消影像選擇，本機引擎回報 `ArgumentException / 0x80070057`。此路徑已移除，沒有放進可執行原型；目前**未解決 KISS 的影像額外開銷**。後續可比較 mpv 的 audio-only 模式，或尋找官方真正的純音訊入口，不需要因此先更換整個介面框架。

後續已加入可選的 mpv 引擎並完成 60 秒對照：KISS 的合計 private 約由 137 降至 51 MiB；詳見 [mpv 實驗](mpv.md)。這是替代播放路徑，不代表原生引擎的限制已修好。

## 已驗證的其他項目

- 核心離線固定資料測試：六台識別、HTML entity／簽章保留、官方表單流程與參數、中廣依名稱選台、格式變動、拒絕未知主機／HTTP／帳密／非預設連接埠、取消與 HTTP 拒絕回應。
- 原生 UI 自動化冒煙測試：清單有六台、靜音控制、停止按鈕、縮小至系統匣、關窗正常退出。
- 編譯使用 warnings-as-errors。

## 解讀限制

- Private bytes 與 working set 意義不同，不能只選較小數字稱為「總記憶體」。
- 只測播放器程序，不含 Windows 共用音訊服務、驅動及部分 GPU 開銷。
- 閒置視窗被隱藏，不等於已量測完整可見介面的成本；UI 冒煙測試與效能測試分開執行。
- 尚未做同電台瀏覽器基準、人工聽音確認、長時間播放、頻繁切台洩漏檢查、封包層斷線驗證、斷網／睡眠喚醒恢復或手機端測試。
- CPU 很低時短測容易受計時解析度與背景負載影響，不應將小數點差異當成精準排名。
- 六台曾成功開播，但飛碟重測有緩衝，不能將「可開播」等同「已可靠播放」。目前不必為介面先引入 Electron、WebView、Rust 或自架代理；KISS 開銷與飛碟穩定性需要另行比較播放引擎。
